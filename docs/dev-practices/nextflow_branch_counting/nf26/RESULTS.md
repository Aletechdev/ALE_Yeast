# Coverage method on Nextflow 26.x (strict parser): probe results, 2026-10-14

Question: does the JaCoCo-on-the-head-JVM method of `tests/nf_coverage.sh` / `tests/nf_coverage_report.py`
(validated on Nextflow 25.10.4, Groovy 4.0.28, `nextflow_code_coverage.md`, `nextflow_branch_counting.md`)
still work on the latest Nextflow 26.x with the strict parser on by default? No pipeline code was changed.
`NXF_SYNTAX_PARSER` was not set: the probe ran on the 26.x default (`Using script parser v2`,
`Using config parser v2` in the log).

Files here (`docs/dev-practices/nextflow_branch_counting/nf26/`, moved from `scratch/nf26_probe/` on commit):
`main.nf` + `probe.config` (strict-syntax probe, 46 + 11 lines, `nextflow lint` clean on 26.10.0 at the first
attempt), `run_probe.sh <NXF_VER>` (one agent run with the `includes` filter of `tests/nf_coverage.sh`, one
without, `jacococli report`, `../xml_lines.py`, javap; writes `out/<ver>/`), `out/ale_lint.txt` (`nextflow lint .`
of the repo under 26.10.0, 2026-10-14, trimmed to git-tracked files: the run also linted local copies and data
directories, see the file header). **Not committed, regenerated by the runner:** `out/<ver>/` (runs with
`.nextflow.log`, class dumps, `.exec`, `probe.xml`, `lines_*.txt`, `javap*.txt`). The two side tests quoted
below were ad-hoc runs (`out/incl_test/`: a `main.nf` including `mods/helper.nf`, `mods/sub/main.nf` and
`mods/other/main.nf`, then a `nextflow.config` with `includeConfig 'inc.config'`, run with the wide filter;
`out/dup_main_test/`: two `Main.<id>.class` from different sources in one `--classfiles` dir); their class
names and messages are reproduced here in full, the dumps are not kept.

## The five answers

### 1. Launcher starts with the agent attached; the `includes` filter is still required

Both versions start and complete the probe with `NXF_JVM_ARGS=-javaagent:…` (exit 0, `[SUCCESS] completed=1`).
Without `includes=`, both die at start-up with the same error (`out/<ver>/run_noincl/stderr.txt`):

    Exception in thread "main" java.lang.NoClassDefFoundError: jdk/internal/reflect/GeneratedConstructorAccessor1

So the filter is still required. A wide filter also works: `includes=*,excludes=jdk.*:java.*:sun.*:com.sun.*`
dumps 3 588 classes and runs clean on 26.10.0 (`out/26.10.0/run_wide/`).

**But the pipeline's own filter string records nothing from scripts on 26.x.** With the exact agent
string of `tests/nf_coverage.sh` (`includes=Script*:_nf_config_*`) the 26.10.0 run exits 0 and dumps 5
classes, all `_nf_config_*`; the script's functions, workflow and closures are absent (`out/26.10.0/classes/`).
The 25.10.4 control dumps 14 (9 `Script_b4215c177f53995b*` + 5 `_nf_config_c423bcd9*`). The failure is
silent: no error, a report with only config lines.

### 2. Class names and the log mapping lines: both changed

Measured from `Parsed script files:` in `.nextflow.log` (the block still exists, same `ScriptRunner` DEBUG
line) and the class dump:

| Compiled unit | 25.10.4 | 26.10.0 |
|---|---|---|
| Entry script (`nextflow run main.nf`) | `Script_<16 hex>` | **`Main`** (fixed name, no hash) |
| Included script (`include { } from`) | `Script_<16 hex>` | **`_nf_script_<16 hex>`** |
| `-c` / top `nextflow.config` | `_nf_config_<8 hex>` | `_nf_config_<16 hex>` |
| `includeConfig`'d file | `Script<MD5 of the content, upper>` (the report script's fallback rule) | **`_nf_config_<16 hex>`** (same form as the top config) |
| Log line per script | `  Script_<hash>: /abs/path.nf` | `  Main: /abs/path.nf`, `  _nf_script_<hash>: /abs/path.nf` |
| Log line per config | `ConfigBuilder - Parsing config file: <path>` | **`ConfigCmdAdapter - Parsing config file: <path>`** |

Evidence: `out/incl_test/run_26.10.0/.nextflow.log` lists `_nf_script_a996c038e841693a: …/mods/helper.nf`,
`_nf_script_034dfe9c5c31490c: …/mods/other/main.nf`, `_nf_script_9ae19bc4c2ee7da0: …/mods/sub/main.nf`,
`Main: …/main.nf`; the 25.10.4 run of the same files lists four `Script_<hash>` lines. Two `main.nf` modules
in different directories get different `_nf_script_` hashes (the hash is not the file name).
`out/incl_test/run_cfg_26.10.0/classes/` has `_nf_config_1b22a9b5427338cf` and `_nf_config_c5e303b97ea5dcd5`
for `nextflow.config` + its `includeConfig`'d `inc.config`; 25.10.4 has `_nf_config_e8c473d2` and
`Script6307A66881E6CC2EF2D334D2E3D38E03` (= `md5sum inc.config`, upper).

What this breaks in `tests/nf_coverage_report.py` (read, not run on 26.x):
- the log regex `^\s+(Script_\w+): (/\S+\.nf)\s*$` (class → file map) matches nothing;
- the `ConfigBuilder - Parsing config file:` regex matches nothing, so `top_cfg` is empty and the line-fit
  mapping of `_nf_config_` classes has no candidates;
- the `'Script' + md5(content).upper()` rule for `includeConfig`'d files never applies (they are now
  `_nf_config_<hash>` and must join the line-fit candidates; the `os.walk` already enumerates them);
- the javap pass selects `f.startswith(('Script', '_nf_config_'))`, which skips `Main*` and `_nf_script_*`.

And one new hazard, measured in `out/dup_main_test/`: **two different `Main` classes in one report fail**.
The probe's `Main.9e169fbabd29b262.class` and the side test's `Main.659f78445d7512be.class` in one
`--classfiles` directory give

    java.lang.IllegalStateException: Can't add different class with same name: Main

On 25.10 every entry script has its own `Script_<hash>` name, so the merged suite report never met this.
Under nf-test every process / workflow test runs its own generated entry script, so a merged 26.x report
must keep exactly one `Main.<id>.class` (the pipeline's `main.nf`, mapped by the log) and drop the rest.

### 3. Per-line branch counts: identical on both versions

`xml_lines.py` on `out/25.10.4/probe.xml` and `out/26.10.0/probe_wide.xml` (`lines_main*.txt`, `lines_config.txt`):

| File:line | Construct | 25.10.4 total (covered) | 26.10.0 total (covered) | Differs |
|---|---|---|---|---|
| main.nf:4 | `if (a && b)` | 6 (6) | 6 (6) | no |
| main.nf:10 | `x ?: y ?: z` | 4 (1) | 4 (1) | no |
| main.nf:15 | `if (!a)` | 4 (4) | 4 (4) | no |
| main.nf:38-39 | `.branch { small: v < 2; other: true }` criteria closure | 4 (3), **no line table** (method line `None`), absent from every per-line count | 4 (3), no line table, absent | no |
| main.nf:41 | `.map { v -> v * 10 }` | 0 | 0 | no |
| probe.config:8 | `ext.args = { a && b ? 'x' : 'y' }` | 6 (0) | 6 (0) | no |
| probe.config:9 | `ext.prefix = { x ?: y ?: 'z' }` | 4 (0) | 4 (0) | no |
| totals | | script 14 (11) + config 10 (0) | script 14 (11) + config 10 (0) | no |

No row differs. Groovy 4.0.28 → 4.0.33 and the strict parser produce the same jump counts for every
construct in the probe (`&&` 6, `!` 4, chained Elvis 4, ternary-on-`&&` 6). The config closures were
never called (ECHO reads no `task.ext`), so covered = 0 on both; their instruction counts differ (25.10:
16/34 and 16/36; 26.10: 0/18 and 0/20), a bytecode-size change that does not touch branches.

Caveat for the pipeline's 916: a probe of 7 constructs says nothing about `switch`, `in`, `instanceof` or
the `task.ext.when == null || task.ext.when` guard; the 25.10 probe table in `nextflow_branch_counting.md`
covers those and was not re-run here. Expect the denominator to move only if the strict parser rewrites a
construct, which it did for the `branch` catch-all (next answer), not for plain conditions.

### 4. The `branch` catch-all no longer compiles to `iconst_1; ifeq`; the constant-jump filter would not match

javap of the criteria closure `…$_closure8.doCall` (`out/<ver>/javap*.txt`):

25.10.4 (as documented):

    32: iconst_1
    33: ifeq          47
    36: ldc           // class nextflow/script/TokenBranchChoice … String other

26.10.0:

    32: getstatic     #73   // Field java/lang/Boolean.TRUE:Ljava/lang/Boolean;
    35: invokedynamic #76   // InvokeDynamic #1:cast:(Ljava/lang/Boolean;)Z
    40: ifeq          54
    43: ldc           // class nextflow/script/TokenBranchChoice … String other

The strict parser (or Groovy 4.0.33) materialises the literal `true` as `Boolean.TRUE` and casts it through an
`invokedynamic` before the `ifeq`. JaCoCo still counts 2 branches for the jump, one of them untakeable, but
`nf_coverage_report.py`'s rule (`iconst_0`/`iconst_1` immediately followed by `ifeq`/`ifne`) **does not match**:
on 26.x the four `mutation_report/main.nf` defaults would return to the counts and the headline would read
514 / 920 again. The filter needs a second pattern: `getstatic Boolean.TRUE|FALSE; invokedynamic cast; ifeq|ifne`,
with the same "not itself a jump target" guard. In this probe the criteria closure has no line table on either
version (the "fifth default" case of the 25.10 doc), so the filter is moot for the probe itself; it is not
moot for the pipeline's four counted defaults.

`NXF_VER=26.10.0 nextflow lint .` (`out/ale_lint.txt`, the lines for tracked files; nothing fixed). Whole directory: 299 files with

(383 errors each), `data/`, `tmp/`, `scratch/` and the 25.10 probe in `docs/`. Restricted to the pipeline

Neither `main.nf` nor `nextflow.config` is accepted. `main.nf`: 26 × "Statements cannot be mixed with script

"Invalid include source" (`includeConfig` of test configs by a computed path, lines 369-374), the

Most frequent messages over the tree: "`x` is already declared" (437), "`x` is not defined" (328), "Variables

estimate asked for, not the work. `modules/nf-core/` errors (17 files) are in unmodified upstream code.

## Closing line

**Coverage method needs 4 changes on Nextflow 26.x strict** (agent `includes` must add `Main*:_nf_script_*`;
report script: log regex for `Main` / `_nf_script_<hash>` and `ConfigCmdAdapter`, `includeConfig`'d files mapped
by line fit instead of the MD5 name, one `Main` class kept per merged report; constant-jump filter gains the
`Boolean.TRUE; invokedynamic cast; ifeq` pattern). Per-line branch counts are unchanged (0 of 7 rows differ,
Groovy 4.0.33). **ALE pipeline strict-syntax migration: 432 errors in 94 files** (pipeline tree; 67 in
`main.nf`, 19 in `nextflow.config`).
